# Codex App-Server Type Generation

<!-- codex-contract-provenance: schema-generation-version=0.147.0-alpha.1.2 -->

The TypeScript and runtime contracts under this directory are generated from
the Codex version in the provenance marker above. The generator rejects any
other local Codex version before it writes output, so compile-time and runtime
validation describe the same protocol.

## Regenerate item notification contracts

```bash
pnpm --filter @bb/agent-runtime generate:codex-contracts
```

This command runs both official Codex generation commands. It copies the
transitive TypeScript import closure of `v2/ThreadItem.ts`, rewrites relative
imports for NodeNext, and extracts the complete JSON Schema definition closure
from `ItemCompletedNotification.json`. The two outputs therefore come from the
same Codex version.

The adapter infers its runtime item type from that JSON Schema, compiles the
schema once, and decodes unknown provider data at its boundary. The boundary
then materialises official schema defaults before it returns an internal item.
Translation policy remains hand-written after that boundary.

## Compatibility fixture evidence

The version-labelled fixtures under `../../__fixtures__` are compatibility
matrices derived from official generated contracts, not provider transcripts.
Each fixture states its exact evidence source. The supported-floor fixture is
derived from `v2/ThreadItem.ts` generated by the official Codex `0.136.0` npm
release and records the npm integrity and generated-file SHA-256. It covers
every discriminant in that historical union. The generation-version fixture
covers every current generated `ThreadItem` discriminant and every field shape
that the translator consumes.

When a generated `ThreadItem` shape changes, update the exhaustive generation-
version matrix. Add another version-labelled fixture only when repository or
upstream evidence proves a distinct structural era. Do not assign an older
Codex version to a shape based only on the current generated contract.

## Refresh other compile-time contracts

```bash
codex app-server generate-ts --out <tmp-dir>
codex app-server generate-ts --experimental --out <tmp-dir>
```

Copy only the contracts required by the hand-written importers. Rewrite their
relative imports to include `.js` extensions for NodeNext.

## Committed state: pruned to the reachable subset

We do **not** commit the generator's full output. The hand-written Codex
adapter imports concrete schema files directly (e.g.
`schema/v2/SandboxPolicy.js`) and never imports the barrels, so most emitted
types are unreachable. The committed tree is therefore pruned to the
transitive type-import closure of the hand-written importers:

- `adapter.ts`, `visibility.ts`, `permission-mapping.ts`,
  `interactive-requests.ts`, `adapter.test.ts`.

At the time of pruning that was 336 of the ~580 emitted files; the
unreachable files and all three `export *` barrels (`index.ts`,
`schema/index.ts`, `schema/v2/index.ts`) were removed. Nothing imports the
barrels, so their removal is type-safe.

### Re-prune after regenerating

The official TypeScript command emits the full set plus three barrels. After
copying the required contracts, delete everything not reachable from the
importers listed above and delete the barrels, then verify:

```bash
pnpm exec turbo run typecheck --filter=@bb/agent-runtime
```

TypeScript reports any over-deletion as a missing-module error; a green
typecheck plus `pnpm exec turbo run test --filter=@bb/agent-runtime` confirms
the kept subset is complete. Keep it pruned to avoid re-vendoring dead types.

## Source of truth

- `schema/*.ts`: generated from Codex app-server, pruned to the reachable subset (see above).
- `runtime/*.ts`: generated JSON Schema used to validate provider values at runtime.
- `index.ts` / barrels: intentionally **not** committed; the adapter imports concrete `schema/**` files directly.
- `packages/agent-runtime/src/codex/event-translation.ts`: translates Codex app-server events into bb thread events.
