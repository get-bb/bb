Multi-Machine v1

Pick the machine a task runs on. Pair new machines over the LAN or through bb connect. Productizing the plumbing that already exists — plan + UI mockups · 2026-07-11

The vision. bb becomes honestly multi-machine: your bb server orchestrates daemons on any number of computers — the laptop it runs on, the Mac Studio on your desk, a cloud dev VM. When you create a task, the environment picker shows where work can happen, grouped by machine. Projects are machine-independent: the project is the logical repo; each machine that has a checkout is a place it can run. Adding a machine is one copyable command that works from anywhere via bb connect, or directly on a trusted network.

Why now / why cheap. Almost all of this was already built and verified in PR #510 (multi-host execution ran a real thread on a second daemon) and then deliberately backed out in #536 as not-yet-productized. The data model, hub routing, per-host auth, and the cloud side of tunnel machine credentials all exist today. This plan is the product shape that lets it re-land and stay.

3The product model

Four nouns, one new relationship:

Machine (host)A computer running a bb daemonHas a name, online/offline status, last-seen. Paired once, via LAN or tunnel. The server's own machine is "this machine."
ProjectA logical codebase — machine-independentAnchored by its git remote when it has one. Owns N sources.
Project sourceA checkout of the project on one machineprojectSources already models this (hostId + path). Guided setup creates one; git automates it, manual link covers non-git.
EnvironmentA working directory on one machineStays machine-local forever (worktree, local checkout, personal). Its hostId decides which daemon executes.

Consequences that keep the model simple:

  • No cross-machine environment identity. A worktree on the Studio and a worktree on the laptop are different environments even on the same branch. Git is the synchronization layer (push/pull), not bb.
  • The picker can be honest. For each machine: does it have a source for this project? Yes → offer local work + worktrees there. No → offer guided setup. Offline → show, disabled, with last-seen.
  • Threads never migrate. A thread's environment pins its machine. If the machine is offline, the thread says so (existing host_unavailable semantics) — same as today, but now the UI names the machine instead of implying bb is broken.
  • Personal workspaces are per-machine by nature. A personal thread targeted at the Studio just uses the Studio's personal workspace. No project source required.

5Pairing architecture

Two transports, one enrollment. In both cases the machine ends up as a normal enrolled host with a bbdh_ host key, holding a daemon WebSocket to the server; the only difference is what carries the bytes.

Path 1 — trusted network (LAN / Tailscale) daemon → server, direct Script hits the server's join-code route with the code, gets an enroll key, enrolls, opens /internal/ws. No cloud involved. This worked in #510 with zero transport changes — the only new piece is the session-authed join-code mint (today enroll keys are loopback-only).
Path 2 — bb connect (headline) daemon → gate → tunnel → server Script first redeems the join code for a bbcm_ machine credential (cloud side already deployed), then performs the same enrollment against https://sawyer.getbb.app with x-bb-connect-machine on every /internal/* request and the WS dial. Gate verifies the credential, strips it, forwards; the server still host-key-auths underneath — defense in depth, verified e2e in #510 with a proxy harness. v1 replaces that harness with real daemon wiring.
One join code, both transports. The "Add a machine" dialog mints a single short-TTL code. The install script inspects --server: a tunnel URL triggers the credential redeem first; a direct URL skips it. The user never chooses a "mode" — they choose an address.
Security invariants to preserve: (1) the gate must keep authenticating /internal/* itself — tunnel traffic arrives at the server as loopback, so unauthenticated forwarding would let anyone mint enroll keys; (2) join-code minting in-product must require an authenticated UI session and mint short-TTL, single-use codes; (3) removing a machine revokes both the host key and (if present) the bbcm_ credential, and severs live sessions.

6Same-machine assumptions & the plugin model

A dedicated audit (2026-07-11) hunted for places that assume the daemon and server share a filesystem. The good news: file preview, diffs, git operations, terminals, thread storage, worktree derivation, and attachments already route through daemon RPC (host.* / workspace.*) — the migration is further along than expected. The breaks cluster in one structural pattern plus a few edges.

6.1 The one structural break: skills & instructions ship paths, not bytes

The server assembles a thread's injected skills by scanning directories on its own disk (builtin skills in the server dist, data-dir/global skills, plugin-contributed skills) and sends the daemon a list of absolute server-machine paths; the daemon then re-reads those paths from its own filesystem and stages them into runtime/global-skills. The wire contract comment says it outright: "all source paths are server-machine paths that the local host daemon reads from its filesystem." On a co-located daemon this works by accident of shared disk. On a remote daemon every path is ENOENT and every skill is silently dropped (staging catches and logs). Same pattern, same fix, three variants:

WhatWhereFailure on remote daemonFix
Builtin / global / plugin skillsservices/skills/injected-skills.ts → host-daemon-contract (sourceRootPath/skillFilePath) → apps/host-daemon/src/injected-skills.tsAll skills silently vanish for threads on that machineSkill sync — see the design below. The daemon-side content-hashed staging stays; the transport changes from "re-read a shared disk" to "fetch missing trees from the server."
Workspace .bb/AGENTS.mdworkspace-agent-instructions.ts:65 — server does fs.readFileSync(workspacePath + "/.bb/AGENTS.md")Project instructions silently dropped from every turnRead via the existing host.read_file RPC on environment.hostId. Not sync — the file already lives on the machine.
Project .bb/skillsthread-runtime-config.ts:188 scans workspacePath/.bb/skills on the server fsProject skills not discoveredEnumerate via daemon RPC (list + read frontmatter). Also machine-resident already — no sync needed.
These are silent failures, not crashes — a remote thread would run with no skills and no project instructions and look "fine." That makes this a hard prerequisite: it moves into M1 as remote-correct thread config, with a regression test asserting a remote thread receives identical instructions/skills to a local one.

Skill sync design (server-owned skills → machines)

Skills are filesystem artifacts — agents read reference files and execute scripts from the skill directory during a thread — so every machine needs real bytes on disk. The daemon already stages skills into content-hashed directories; sync formalizes that as a lazy, content-addressed pull:

  • Store: daemon keeps <dataDir>/runtime/skill-store/<treeHash>/ (today's global-skills/<hash> staging, promoted to a cache with LRU GC).
  • Manifest, not bytes, at thread start: the server sends each skill as {name, treeHash, entryPath}. The server computes tree hashes when it scans sources (it already reads every file for frontmatter).
  • Pull on miss: for hashes not in the store, the daemon fetches a tarball from a new internal route (GET /internal/skills/tree/:hash) over the existing authed transport — the same pattern as project-attachment fetch, so it works identically over LAN and through the tunnel (machine credential + host key).
  • Updates are free: edit a skill → new hash → next thread pulls the new tree; unchanged skills never re-transfer. Dedupes across threads, projects, and plugin/builtin/global sources.
  • Optional warm-up (fast-follow): on daemon connect, the server can send the current hash set so machines prefetch before the first thread — pure latency optimization, same mechanism.

Direction matters: server-owned skills sync down (builtin, global, plugin); machine-owned files are read in place (workspace .bb/AGENTS.md, project .bb/skills live in the checkout on that machine and must not be synced up or overwritten).

6.3 Plugin model: verdict — architecture unaffected, two concrete gaps

Plugins stay server-side and multi-machine doesn't change that. The audit confirmed: plugin JS loads and runs only in the server process (jiti import); background services (including connect's tunnel), schedules, KV/SQLite/secrets storage, mention providers, and contributeInstructions are all server-local. Crucially, the two round-trips already flow the right way — agent tool calls go daemon → server (POST /session/tool-call, handler runs on the server), and plugin CLI commands proxy CLI → server. Plugins that touch workspace files (secrets, inline-vis) already do it through bb.sdk.files.* with an explicit hostId, which routes as host.*_file RPCs — daemon-safe today. Plugin install stays per-server; nothing needs to be copied to machines except:

  • Plugin-contributed skills break — they ride the same paths-not-bytes wire as §6.1 (a remote daemon can't read <serverDataDir>/plugins/<id>/skills). The §6.1 fix covers plugins automatically; no plugin API change needed.
  • bb connect expose <port> exposes the server machine's loopback. An agent starting a dev server on a remote machine can't be reached through connect port-sharing. v1: document the limitation; fast-follow: daemon-side port forwarding (expose a remote machine's port through its daemon connection).
  • Ergonomic gap, not a break: plugin tool/CLI contexts carry no hostId/workspace path — plugins must resolve it via bb.sdk.threads.get(include: "host"). Worth adding hostId to PluginAgentToolContext/PluginCliContext as polish so plugin authors fall into the pit of success on multi-machine.

10Fast-follows (explicitly not v1)

  • Remote daemon updates — SHIPPED (S13) — the server is the distribution source: it serves its own bb-app tarball at /install/bb-app.tgz (+ /install/version), the install script prefers it over npm (so unpublished/dev versions work), and daemons self-update on protocol_version_mismatch when the server is strictly newer (flag-gated on by default from the script, rate-limited, downgrade-refusing). Rejected daemons surface as "Needs update (50 vs 51)" in the Machines pane instead of plain offline.
  • Queue-until-online — create a task against an offline machine, dispatch on reconnect.
  • Per-machine capability toggles — e.g. "no dangerous permissions on the shared VM," provider CLI availability per machine.
  • LAN-direct fast path — tunnel-paired daemons detecting a direct route for latency-sensitive traffic (terminals).
  • Ephemeral / pooled host types — HostType today has the single value persistent; cloud burst machines are a different project.
  • Placement policy — any scheduling beyond "you pick, sticky per project."
  • Non-git directory sync — rejected for v1; git remains the only sync layer.
  • Remote port exposure — bb connect expose for ports on non-server machines (daemon-side forwarding); v1 documents the limitation.
  • hostId in plugin tool/CLI contexts — ergonomic polish so plugin authors get multi-machine right by default.
  • Client-side "open in editor" routing — open files from remote environments in the editor on the machine you're sitting at.
