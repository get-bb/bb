### Terminal
- Protocol: JSON over WebSocket `GET /ws/terminals/:terminalId?sinceSeq=N` (`apps/server/src/server.ts:522-567`; guard is Origin-only, no auth: `browser-request-guard.ts:147-158`). Client→server: `input{dataBase64}`, `resize{cols,rows}`, `close`, `ping`; server→client: `attached{session,replayStartSeq,nextSeq}`, `output{chunk:{seq,dataBase64}}`, `session-updated`, `exited`, `error{code}`, `pong` (`packages/server-contract/src/api/terminals.ts:190-256`). Base64 chunks ≤64 KiB (`packages/domain/src/terminal.ts:5`). Server relays daemon `terminal.output` (`terminal-session-lifecycle.ts:1437-1453`); attach requests daemon replay tail 512 KiB (`:1309`, const `:55`); daemon keeps 4 MiB/10k-chunk scrollback via node-pty (`apps/host-daemon/src/terminals/terminal-manager.ts:6,20-21,731-750`).
- HTTP fallbacks exist: `POST /terminals/:id/input|resize`, `GET /terminals/:id/output?sinceSeq&tailBytes` (polling), create/close/restart/rename (`public-api.ts:690-761`, SDK `packages/sdk/src/areas/terminals.ts:209-290`). Create target kinds thread|environment|host_path (`terminals.ts:62-83`).
- Client: `TerminalWebSocketTransport` (`terminal-websocket-transport.ts:60-400`) is headless: injectable `createSocket`, reconnect backoff, heartbeat 15s/45s, input queue 1 MiB, seq-gap detection; only DOM-ish need is `new URL(url).searchParams` (`:36-40`). `ThreadTerminalView.tsx` is xterm.js: dynamic imports of `@xterm/xterm`, addon-fit, web-links, unicode11, optional webgl (`:789-797`), theme built by probing CSS vars via `getComputedStyle` (`:228-285`), `ResizeObserver` fit (`:986-992`), touch-to-focus for iOS keyboard (`:719-758`), `btoa/atob/TextEncoder` (`:351-410`). URL builder uses `window.location` (`terminal-websocket-url.ts:19-20`).
- Controller `useThreadTerminalController.ts` (755 lines) is React Query + fixed-panel-tabs state; no DOM.

## Risks
- Terminal in a WebView: the server accepts the terminal WS only if `Origin` is trusted or absent (`browser-request-guard.ts:152-158`); a WebView page loaded from a bundled/`file://`/`about:blank` document may send `Origin: null` or a custom-scheme origin that fails `isTrustedOrigin` — verify or have RN own the socket (reusing `TerminalWebSocketTransport`) and bridge chunks into the WebView via postMessage. Bridging base64 chunks ≤64 KiB per message through `injectJavaScript` may bottleneck on heavy output; batching required.
- Terminal replay/resize semantics: `attached.replayStartSeq` vs client `nextOutputSeq` gap handling resets the terminal (`ThreadTerminalView.tsx:939-945`); onData replies during replay must be suppressed (`forwardTerminalData`, `:379-401`) — any WebView port must preserve the `write(data, cb)` suppression counter or the PTY receives spurious DA1 replies (see `terminal-manager.ts:27-35`).
- iOS keyboard + xterm in WKWebView: focus/keyboard requires a user gesture; existing web build already needed touch-to-focus hacks (`ThreadTerminalView.tsx:719-758`). Hardware-keyboard modifiers and Ctrl-key entry on soft keyboards need a native accessory bar (not present in web).
- `@pierre/diffs` core import may register a custom element / touch `HTMLElement` at module evaluation (custom element `diffs-container`, `DIFFS_TAG_NAME` export) — importing it in Hermes for the parser alone is unverified; may need a standalone unified-diff parser.
- Hermes globals: `TextDecoder` (used in `file-preview.ts:3-4` and Pierre), `URL.searchParams` (`terminal-websocket-transport.ts:36-40`), `structuredClone`, `Worker` — need polyfills or version pinning; `ThreadDetailWorkerPoolProvider` already guards `typeof Worker === 'undefined'` (`:24`).
- Diff viewer parity: Pierre features used — split/unified toggle, wrap/scroll, expand-context (via `/diff/file` sides), gutter line selection → 'add to chat' patch text, image/SVG previews, sticky headers, per-card collapse, viewport-driven patch paging with 50-path batches — a native rewrite must reimplement or consciously drop these; a WebView embed keeps parity but loses native scrolling feel and complicates 'add to chat' (needs postMessage bridge).
- HTML/iframe previews: server serves worktree/raw HTML with CSP `sandbox allow-scripts` (`threads/data.ts:124`, `files.ts:33`); a WebView loading these URLs must be pointed at the reachable server origin (bb connect / LAN) and will not be able to reach the host's localhost dev servers.
- Panel tab state is dual: server-synced thread tabs (revision-checked `PUT /threads/:id/tabs`, 409 on conflict) plus device-local fixed-panel state in localStorage (`fixed-panel-tabs-state.ts:24-27`) — RN needs a storage adapter and must respect the same tab-kind schema so desktop/web/mobile stay in sync; tab kinds unsupported on mobile (browser, plugin-panel, side-chat) still arrive from other devices and need a graceful placeholder.
- In-app browser: no server contract exists; the plans (`plans/bb-browser.md`) target Electron CDP automation. An RN WebView browser tab is feasible but any 'agent-visible browser automation' parity is out of scope until server routes exist.
- Workspace open targets and 'Open in editor/terminal app' fundamentally rely on a local daemon on the viewing machine; on mobile these must be hidden or redesigned (e.g., 'open on host X' server-proxied action, which needs a new daemon RPC and protocol version bump).
- Realtime invalidation of diff/work-status/terminals-changed rides the main `/ws` realtime socket (`realtime-cache-registry.ts:394,433`); the RN app must run the same realtime client (SDK `realtime-client.ts`) or diff/terminal lists go stale.
