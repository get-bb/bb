1. What this is, in plain words

Think of bb's sidebar as a shelf that bb builds. Until now, only bb could build it. This change adds a hole in the wall: a plugin can hand bb a different shelf, and bb hangs it in the same place.

Three rules keep that safe:

  • bb's shelf is the default. Installing a plugin never takes your sidebar.
  • You choose in Settings, and the choice lives on your device.
  • If the plugin breaks or leaves, bb's shelf comes back — you are never left with an empty sidebar.

The example plugin, t3sidebar, uses that hole to build an inbox. Its one big idea: the list never re-orders itself. In bb's own sidebar, a row can slide away while you are reading it, because activity moves things. Here, a thread takes a spot when it is created and keeps it until you file it away. Status is drawn inside the card instead of being shown by its position.

2. The main loop: switch, use, switch back

The setting is one dropdown. It only appears if you actually have a sidebar plugin installed, so nobody else sees a control that does nothing.

Picking the plugin swaps the sidebar immediately — no reload. Picking bb again swaps it straight back.

Why the "New thread" row matters here. t3sidebar brings its own header, so bb hides its own. If bb forgot to un-hide it when the plugin vanished, you would lose the New-thread button and the search box with no way to get them back. That path is now handled for a crash and for a disable.

3. Parking work: settle and snooze

An inbox is only useful if you can empty it. Hover any card and the status is replaced by two buttons: snooze (bring it back later) and settle (I am done with this).

One rule matters more than the rest: a thread that is working can never be parked. If you could hide running work, you would eventually hide something you needed. So while a thread is busy, the park buttons are simply not there:

4. Where child threads went

A flat list has nowhere to nest a child thread. So t3sidebar takes them out of the list and puts them on their parent's header instead — a small chip that opens the list of children. Clicking one goes there.

The trap this avoids. A child is hidden only when its parent is on screen. If the parent is archived, deleted, or filtered out by the project scope, the child stays in the list — otherwise it would be hidden in the list and absent from any header chip, which means unreachable.

6. The API, layer by layer

The change is five stacked PRs. Each one builds and tests on its own, so they can be reviewed and landed in order.

PRWhat it addsWhy it is separate
#924app.slots.experimental_threadListThe hole in the wall, plus the setting and all three fallback paths.
#925experimental_useSidebarThreads
experimental_useSidebarThreadActions		The data. Reads bb's own cache, so a plugin list costs no extra network calls and updates on the same events.
#926experimental_useSidebarThreadSplit
experimental_ThreadContextMenu		The two behaviours a plugin cannot rebuild: drag-to-split and the shared menu.
#927app.slots.experimental_threadHeaderActionA control in the thread header — where the hidden children went.
#928the t3sidebar pluginProof the API is usable, and the example other authors copy.

Two decisions worth your attention

Status icons are data, not a component. bb tells the plugin which status a thread has (indicator) and the screen-reader wording for it, then gets out of the way. The plugin draws its own icons. A sidebar that cannot pick its own icons is not really replaced.

Dangerous actions stay with bb. There is deliberately no silent delete in the plugin API. Deleting a thread also deletes its children, and only bb can show the dialog that counts them first. A plugin can request a delete; bb asks the user. Archiving likewise runs bb's full flow, so open panes are closed and the URL is repaired.

Where the plugin's own data lives

"Settled" and "snoozed" are t3sidebar's ideas, not bb's. They live in the plugin's own small database. That means no change to bb's thread schema, no change to the server↔daemon protocol, and uninstalling the plugin takes its data with it. Confirmed directly:

$ sqlite3 …/plugins/t3sidebar/data.db "SELECT * FROM thread_lifecycle;"

Each layer was reviewed by a separate Codex GPT-5.6-Sol agent before the next one was built. Those reviews caught real problems that are now fixed, including:

  • a crashed list-and-actions plugin left the user with no New-thread button;
  • the plugin action API accepted a split option and silently ignored it;
  • delete skipped bb's confirmation dialog and its pane cleanup;
  • a crash in one split pane's header control disabled it in every pane;
  • the settle and snooze buttons were built but never actually rendered.

One review finding I declined: a reviewer asked for an experimental_ prefix on the new type exports. bb's existing convention prefixes the runtime member only — experimental_NewThreadComposer ships with a plain NewThreadComposerProps, and there are zero prefixed type exports in the contract today. Following the reviewer would have made this API inconsistent with the one beside it.

Live testing also found two bugs the tests had not: an empty inbox with everything parked hid the shelves entirely, and the host's header clamp clipped the plugin's own popover. Both are fixed, and the first now has a regression test.

9. Try it yourself

scripts/bb-dev-app branch sidebar/t3sidebar-plugin
eval "$(scripts/bb-dev-app env)"
bb plugin enable t3sidebar
# then: Settings → Appearance → Sidebar → "t3sidebar (inbox)"

Things worth poking at: hover a card and settle it; watch a running thread refuse to be parked; right-click a card; Ctrl/Cmd-click one; fork a thread and look at the header chip; then switch back to bb's sidebar and confirm nothing was lost.

10. What I need from you

  1. Is the split right? Status as data (plugin draws its own icons) but the context menu as a shared component. That is the one inconsistency in the API, and it is deliberate.
  2. Two APIs now share the thread header row — the new slot and the older backend bb.ui.registerThreadAction. The row already holds five host controls. Should there be a cap or an overflow before a third plugin adds one?
  3. Should the sidebar choice sync across devices? It is per-device today, which is safe when a plugin is not installed everywhere, but may surprise someone with two machines.
  4. Is t3sidebar the right example to ship bundled? It is off by default and never turns itself on.
