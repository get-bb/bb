# Community forms

`/community/survey` serves up to ten required questions, depending on earlier answers, followed by required email. `/community/merch?c=CODE` validates an issued code and opens an encrypted Jotform form. Both are standalone documents with the shared site navigation and footer, no analytics, `noindex, nofollow`, `Cache-Control: no-store`, and a restrictive Content Security Policy. The survey uses `Referrer-Policy: same-origin` to support its POST; merch pages, external form links and embeds suppress referrers so bearer codes cannot reach analytics on other pages. Neither appears in navigation or the sitemap.

The navigation and footer hydrate independently; the form stays server-rendered so option shuffling and POST responses retain their existing behavior. Their client bundle is generated by `pnpm exec turbo run generate:site-chrome --filter=@bb/web`, a dependency of the web build, tests, typecheck and Turbo dev task. Regenerate it after editing shared chrome during development. The generated script is loaded with the response nonce and requires no additional CSP permissions. The Vite build copies emitted SSR static assets into the client asset directory, including the form stylesheet and chrome bundle. Server JavaScript chunks remain private.

## Configuration and launch

Collection defaults to off in both environments. `COMMUNITY_FORMS_ENABLED=true` enables survey submissions and the configured Jotform embed. Keep it off until the copy, data handling and exact build pass review. Apply the generated connect-db migrations before enabling collection.

`COMMUNITY_JOTFORM_URL` defaults to an empty string. Set it to the encrypted form's HTTPS URL on `form.jotform.com` or `form.jotformeu.com`. An empty or invalid URL shows the warm thank-you with a form-not-open notice, never an address form hosted by bb. The form must have a field whose unique name is `code`; bb prefills that query parameter. Verify encryption, prefill and decryption with a synthetic submission before launch. A URL alone cannot establish that encryption is enabled.

Configure the Jotform fields as name for the label, address, country, and an optional note. Do not ask for email, phone or Discord. Configure its submit label as “send me merch” and its confirmation as “you're in! 🎉 we'll ping you on discord when it's on the way. ty for being here.” Keep the decryption access code with the person packing the envelopes.

`COMMUNITY_MERCH_INVITE_HASHES` is an optional private Worker secret containing a JSON array of SHA-256 hex hashes of contributor invitation codes. Generate unpredictable codes with at least 128 bits of entropy and send the raw code only in the personal link. Remove its hash after fulfillment to revoke access. Survey sticker codes use their own database pool.

The shared review preview keeps collection off and the form URL empty. Local synthetic QA may override these values against a fresh local D1 database; never use production bindings or real addresses for QA.

## Survey submission contract

POST `application/x-www-form-urlencoded` to `/community/survey` with the `submission_id` UUID from the page. The question fields, in page order, are `discovery`, `role`, `work`, `company_size`, `love`, `improve`, `team_improve`, `team_adopt`, `community`, `city` and `meetup`; `survey.ts` owns their labels and choices. Questions are numbered in the browser, so hidden questions don't use a number.

Every visible question is required. Radio answers accept one listed choice. `community` is a checkbox that accepts one to three listed choices, each repeating the field name; the browser disables the rest once three are picked. `meetup` is a radio. Text answers must not be blank.

`work` is hidden when `role` is “Student” or “Not currently working”, and so are the three questions that depend on it. `company_size` is shown for any `work` answer except “I don't use bb for work”. `team_improve` is shown for “2–4 people” and “5 or more”. `team_adopt` is shown for “Just me”. A hidden question is cleared and disabled in the browser, and discarded before server validation and storage, so it is never required.

Q1 shuffles every choice except “I don't remember” and “Other”, which stay last in that order. The community question shuffles every choice except “Other”, which stays last. Other questions keep their listed order. Picking “Other” on `discovery`, `role` or `community` shows a “Please specify” text box below the choices; its `discovery_other`, `role_other` or `community_other` text is then required, and otherwise discarded. The meetup label names the city once one is typed.

`email` is required, accepts one valid address, and is stored with the answers in the private survey response. Text fields accept up to 250 characters. Removed questions and contact fields are rejected.

The browser saves progress, including email, in `localStorage` under `bb-community-survey` and restores it on a later visit when the server didn't return answers. The completion page removes it.

The request's `Origin` must match the page origin. A 16 KiB body limit and six submissions per minute per client apply; IPv4 clients are keyed by address and IPv6 clients by their /64 network. Unknown fields are rejected. Validation returns HTTP 400 with answers preserved, collection-off or storage failure returns 503, rejected origin returns 403, and rate limiting returns 429. Merch accepts GET only; bb has no address POST endpoint.

## Gifts, sticker pool and privacy

The gift is bb stickers. Exhausted codes show “We've given out all the stickers for now. Thank you for answering.”

A successful survey save atomically allocates a random one-use sticker code while stock remains, at most one per email. Email is compared lowercased and trimmed with any `+tag` removed; a repeat email saves its answers and shows “This email already has a sticker code.” `community_survey_email` keeps only a SHA-256 of that normalized email. Allocation picks a random unused slot so slot order cannot reveal response order. The database caps slots at 250, and a duplicate submission UUID cannot allocate another code. The confirmation links to `/community/merch?c=CODE`; exhausted stock uses the sold-out line. Reposting a saved submission shows a received-response message; it cannot recover its code because no response-to-code mapping exists. Save the original claim link.

Survey responses contain a random submission ID, creation time and answers, including email. Email is used for stickers and results, never a marketing list. `community_sticker_code` contains only a pool slot, code hash and shipped flag: no survey ID, answer, contact detail or timestamp. Raw codes are never persisted. Do not add request-body logging, analytics, or a join between these datasets. Infrastructure may still handle request metadata; review logging before launch. IP addresses are used by the short-lived rate limiter, not stored with answers.

GET does not consume a code: people must be able to reopen the mailing form. One-use means one fulfilled pack. The shipper decrypts Jotform submissions and validates each code against the issued hashes before sending, skipping unknown codes and codes already shipped. The external form is public, so this fulfillment check is mandatory even if a submitted code was prefilled.

After shipping, set `community_sticker_code.shipped = 1` for the matching SHA-256 hash, or revoke the contributor hash. Retain all sticker slots, including shipped slots, to preserve the lifetime cap; never delete them to replenish stock. Keep only a separate code/pack/shipped-date ledger. Delete the address response from Jotform and request deletion of any label-provider copy. bb never stores addresses.

Choose a survey closing date and response-deletion date before launch. Delete raw survey responses when no longer needed and retain anonymous aggregate findings. Database backups can retain deleted survey answers under the provider's recovery policy.
