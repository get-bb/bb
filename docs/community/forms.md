# Community forms

`/community/survey` is a site page with up to eleven required questions, depending on earlier answers, followed by required email. It uses the shared site navigation and footer, runs no analytics, and is `noindex, nofollow`. It doesn't appear in navigation or the sitemap. The page posts answers as JSON to `/api/community/survey`. Its form also declares `method="post"` to that route, so a submit before the page script loads never puts answers in a URL; the route rejects that non-JSON post.

## Configuration and launch

Collection defaults to off in both environments. `COMMUNITY_FORMS_ENABLED=true` enables survey submissions. Keep it off until the copy, data handling and exact build pass review. Apply the generated connect-db migrations before enabling collection.

Sticker claims need four Shopify settings. `COMMUNITY_SHOPIFY_STORE` (the `*.myshopify.com` host) and `COMMUNITY_STICKER_VARIANT_ID` (the numeric sticker-pack variant) are vars: empty in staging, set in production. `SHOPIFY_CLIENT_ID` and `SHOPIFY_CLIENT_SECRET` are Worker secrets from a Dev Dashboard app installed on the store with only the `write_discounts` scope; `deploy-web.yml` syncs them from GitHub secrets and skips them while they are empty. `COMMUNITY_STICKER_LIMIT` caps how many claims are reserved (1000). Until all four Shopify settings exist, finishers see “Sticker claims aren't open yet.” Nothing is loaded into the database. The Shopify secrets aren't in `secrets.required`, so deploys succeed before setup; for local QA, set them as vars, because local dev loads only the listed secrets from `.dev.vars`.

The shared review preview keeps collection off. Local synthetic QA may override these values against a fresh local D1 database; never use production bindings or real addresses for QA.

## Survey submission contract

POST `application/json` to `/api/community/survey` with `{ "submission_id": "<uuid>", "answers": { "<field>": ["<value>", ...] } }`. The page creates the UUID once per attempt, so a retried send is saved once. The question fields, in page order, are `discovery`, `role`, `work`, `company_size`, `love`, `improve`, `team_improve`, `team_adopt`, `community`, `city`, `meetup` and `research_call`; `survey.ts` owns their labels and choices. Questions are numbered in the browser, so hidden questions don't use a number.

Every visible question is required. Radio answers accept one listed choice. `community` is a checkbox that accepts one or more listed choices. `meetup` and `research_call` are radios. Text answers must not be blank.

`work` is hidden when `role` is “Student” or “Not currently working”, and so are the three questions that depend on it. `company_size` is shown for any `work` answer except “I don't use bb for work”. `team_improve` is shown for “2–5 people”, “6–10 people” and “More than 10”. `team_adopt` is shown for “Just me”. The page and server share these rules (`questionVisible` in `survey.ts`); a hidden question is never required and its answer is never sent or stored.

Q1 shuffles every choice except “I don't remember” and “Other”, which stay last in that order. The community question shuffles every choice except “Other”, which stays last. Other questions keep their listed order. Picking “Other” on `discovery`, `role` or `community` shows a “Please specify” text box below the choices; its `discovery_other`, `role_other` or `community_other` text is then required, and otherwise discarded. The meetup label names the city once one is typed.

`email` is required, accepts one valid address, and is stored with the answers in the private survey response. Text fields accept up to 250 characters. Removed questions and contact fields are rejected.

The page saves progress, including email, in `localStorage` under `bb-community-survey`, restores it on a later visit, and removes it once the answers are saved.

Requests must be JSON, which cross-site forms can't send without a CORS preflight the route never allows. A 16 KiB body limit (checked against `Content-Length` when sent, and counted in bytes while the body streams, which stops reading past the limit) and six submissions per minute per client apply; IPv4 clients are keyed by address and IPv6 clients by their /64 network. Unknown fields are rejected. Success returns `{ "result": { "duplicate", "claimLink", "claimNote", "emailStatus" } }`. Validation returns HTTP 400 with `errors` by field, an unreadable body returns 400, collection-off or storage failure returns 503, and rate limiting returns 429, each with an `error` message. The page keeps the answers on screen after any failure.

## Gifts and sticker codes

The gift is two bb stickers, claimed through a Shopify store. Each claim gets its own Shopify discount, created when the claim is made: no code list is stored or loaded.

The save is one D1 batch: it checks whether the normalized email already has a claim, inserts the response, reserves a claim (`community_sticker_claim`, with a random `BB-` code of 12 base32 characters) only when the response is new, claims are configured, the email has no claim and fewer than `COMMUNITY_STICKER_LIMIT` claims exist, and records the email's SHA-256 in `community_survey_email` only when the claim was reserved. Email is compared lowercased and trimmed with any `+tag` removed. Someone who finishes while claims are closed or sold out can still claim later with the same email.

After the batch, the worker gets a client-credentials token and calls `discountCodeBasicCreate` (Admin GraphQL 2026-10) with the stored code: $3.00 off the sticker variant, usage limit 1, no combining, tagged `survey`, titled `Survey stickers – <first 8 characters of the submission ID>`. Each Shopify request times out after 5 seconds and refuses redirects. A duplicate-code error or an ambiguous failure is resolved by looking the code up with `codeDiscountNodeByCode`; the stored code is reused for every attempt, so retries never create a second discount. On success the claim becomes `created`; otherwise it stays `pending`. Pending claims are retried, and their links emailed, by the hourly job below. `claims.ts` owns the whole claim: the save batch, the Shopify step and the messages.

`claimLink` is `https://<store>/cart/<variant>:1` with `discount=<code>` and `checkout[email]=<email>`, so checkout opens with the pack, the code applied, a $0 total and the email filled in. The thank-you view shows it once. `claimNote` is null when a claim was reserved, “This email already has a sticker code. Thank you for answering again!” when the email already claimed, “We've given out all the stickers for now. Thank you for answering.” at the limit, and “Sticker claims aren't open yet. We'll post in Discord when they are.” without Shopify settings. A duplicate submission UUID cannot claim again.

## Results email

A claim with status `created` is an email waiting to send; there is no separate queue table. Right after the code is created, the worker sends the email through Resend (`RESEND_API_KEY`) from `updates@mail.getbb.app`: the claim button, then the filled-out survey from “Getting to know you” on, with the chosen options highlighted. The address and answers come from the survey response and the link is rebuilt from the stored code. The send is retried once right away. On success one batch sets the response's `emailed_at` and makes the claim `delivered` with its `submission_id` cleared. Every attempt uses the idempotency key `community-survey/<response id>`, which Resend honors for 24 hours; a duplicate email is possible only if a success went unrecorded and the retry came more than a day later, which is accepted. A repeat email, a save at the limit, or claims closed gets no message.

An hourly cron trigger (`runClaimRetries`) first expires every pending or created claim older than 30 days (status `expired`, `submission_id` cleared), then emails up to 100 created claims older than 5 minutes, then creates codes for up to 100 pending claims older than 5 minutes and emails them in the same run, least recently attempted first. The pending pass stops at the first auth or unreachable Shopify failure, since later claims would fail the same way, which keeps a run far inside the 15-minute cron limit. Any run that leaves something undelivered writes one `community_sticker_deliveries_stuck` log line with the number of undelivered claims, the oldest one's age and the last failure (`auth`, `unreachable`, `rejected` or `email`). With Shopify and Resend healthy, a backlog of N clears within ceil(N / 100) hourly runs plus the 5-minute delay. Nothing in recovery edits the database by hand: fixing the Shopify or Resend setup lets later runs finish the backlog.

`emailStatus` is `sent` when the email went out, `queued` when a claim is waiting for its code or its email, and `none` when nothing will be sent. The thank-you view says “We've emailed you your results.”, “We'll email you your results shortly.” (with a link) or “We'll email you your results and sticker link shortly.” (pending). A repeat send reports that submission's status: “Check your email for your results and sticker link.” when sent and “We'll email you your results and sticker link shortly.” when queued. A failed send never fails the submission. The email repeats the finisher's written answers, like a form receipt; because the address isn't verified, a submitter can send that text to any address, once per address and only while claims remain. This is accepted.

The store must not accept payments, so a cart without a code or with more than one pack cannot be completed. Shopify keeps each order's name and mailing address; fulfill orders from Shopify admin and mark them fulfilled there. bb never stores addresses.

## Privacy

Survey responses contain a random submission ID, creation time and answers, including email. Email is used for stickers and results, never a marketing list. A claim links a response to its code through `submission_id` only until the claim is delivered or expires; the email hash holds no answers. When raw responses are deleted, skip any response a claim still links to (pending or created) until it is delivered or expires. Claim rows (counts toward the limit) and email hashes (one claim per email) are kept. Do not add request-body logging or analytics. Infrastructure may still handle request metadata; review logging before launch. IP addresses are used by the short-lived rate limiter, not stored with answers.

Choose a survey closing date and response-deletion date before launch. Delete raw survey responses when no longer needed and retain anonymous aggregate findings. Database backups can retain deleted survey answers under the provider's recovery policy.
