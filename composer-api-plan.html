BB-71 · API design v2 · 2026-07-20

Composer Plugin API — components in slots, hooks for behavior

Replace the single composerAccessory footer slot with app.composer.customize(): plugin React components mounted in semantic composer slots (right-side actions, banner stack), small data contracts only where the host must own interaction (the + menu, editor text decorations), and behavior expressed through the existing useComposer() hooks — context-bound to the composer instance that mounted the slot.

1 · Decisions at a glance

Design questionDecision
Core primitiveComponents in slots + imperative hooks. Action buttons and banners are plugin React components; onClick → plugin state → hook calls (setText, setTextEffect, setInputLock) → cleanup. No transform(original) pipeline, no host-rendered action contract, no state()/run() vocabulary. Rationale in §3.
Where components can't goTwo places, for mechanical reasons: + menu items (Radix owns keyboard nav, focus restore, and the mobile sheet — items are a small data contract) and inside the editor text (ProseMirror owns those nodes — paint goes through declarative decoration rules).
Composer identityContext binding, not ids. A slot component's useComposer() / useComposerView() are bound to the composer instance that mounted it (the existing PluginComposerHost mechanism). Nothing to pass around; calls from outside a composer subtree keep today's scope-resolution fallbacks.
Native controlsNot removable, hideable, or reorderable. Submit / stop / queue / voice / attach / native menu items and cards are host-owned invariants — structurally, since there is no API through which they could be dropped.
Text effectsOne decoration engine, two sources, zero vocabulary. An effect is a class name from the plugin's own stylesheet applied to decoration spans. Content-derived: declarative rules (match(text) → ranges). State-derived: imperative setTextEffect({ className }) (widened from today's "shimmer" enum). BB's shimmer + ultracode highlight become host-registered users of the same engine. Decorations never mutate the document.
Input lockNew composer.setInputLock(locked): host makes the editor read-only + aria-busy, keeping cancel reachable. Auto-released on unmount / scope change / reload, so a crashed plugin cannot wedge the composer. Closes Improve Prompt's type-during-rewrite race.
Chrome consistencyVia the SDK's existing philosophy: plugins vendor BB components (npx shadcn add @bb/<name>) — the docs ship an icon-button recipe matching native sizing and coarse-pointer targets. Accessibility of custom components is the plugin's responsibility.
OrderingPlugins sorted by pluginId asc (existing snapshot order), registrations in call order within a plugin, entries in array order. Deterministic; no priorities.
IsolationEvery slot mounts inside its own PluginSlotMount error boundary; a crashing action button or banner collapses only itself. Menu-item run errors toast + log. The native composer never degrades.
pendingInteractionReplaces the editor as today: action slots, + entries, and decoration rules suspend with it; banners stay mounted (they annotate the thread, not the editor).
composerAccessoryKept for one compatibility window as a mapped legacy footer slot, @deprecated; removed next SDK major. useComposer() is not deprecated — it's the backbone of the design, gaining setInputLock and the widened setTextEffect.
Wire impactFrontend-only (SDK contract + app). No server/daemon payload changes ⇒ no HOST_DAEMON_PROTOCOL_VERSION bump.

3 · Why components + hooks (and why not a transform)

Components fit the SDK BB already has. The plugin SDK deliberately removed frozen component prop types in favor of vendored components plugins own; composerAccessory, banners, panels, and settings sections are already components; and useComposer() already carries the safe imperative operations. Making action buttons components too means one mental model everywhere — "render UI in a slot, call hooks for behavior, hold your own state" — instead of a parallel data-contract vocabulary (state() selectors, run() contexts, pending-effect declarations) that this design's earlier drafts kept accreting.

A literal transform(original) was still rejected as the outer shape: an arbitrary function over the whole composer definition makes "preserve native entries" a runtime-diffing policy problem, lets one plugin's corrupt output poison the next plugin's input, and freezes the entire composer definition as public API. Slots make preservation structural — there is no field through which submit or voice could be dropped — and one plugin failing removes exactly its own mounts.

The two non-component regions are mechanical, not stylistic. Menu items must be host-rendered DropdownMenuItems or Radix's keyboard navigation, focus restoration, and mobile bottom-sheet rendering break. Editor text paint must be ProseMirror decorations issued from inside the editor, or the view/state mapping corrupts — no component can wrap text ranges the editor owns.

4 · Authoring model — Improve Prompt, complete

app.composer.customize({
  id: "improve-prompt",
  scopes: ["thread", "new-thread", "side-chat"],   // optional; default: all scopes
  actions: [{ id: "improve", component: ImproveAction }],
});

function ImproveAction() {
  const composer = useComposer();       // bound to THIS composer instance via context
  const view = useComposerView();       // reactive: scope, layout, draft, run state
  const [busy, setBusy] = useState(null);   // AbortController | null

  async function improveNow() {
    const ctl = new AbortController();
    setBusy(ctl);
    composer.setTextEffect({ className: "ip-shimmer" });   // class from this plugin's CSS
    composer.setInputLock(true);                           // read-only + aria-busy
    try {
      const better = await improve(composer.text, { signal: ctl.signal });
      composer.setText(better);                            // mention-safe replace
    } finally {
      composer.setInputLock(false);
      composer.setTextEffect(null);
      setBusy(null);
    }
  }

  // Vendored BB icon button — same chrome as the native mic/submit controls.
  return (
    <PromptIconButton
      icon={busy ? "Spinner" : "Sparkles"}
      label={busy ? "Cancel improve" : "Improve prompt"}
      disabled={view.draft.isEmpty && !busy}
      onClick={() => (busy ? busy.abort() : improveNow())}
    />
  );
}

No registration-level behavior contract: visibility, disabled state, progress, and cancellation are ordinary React state. If the slot unmounts mid-run (scope change, reload), the lock and effect auto-release and the component's own cleanup aborts the fetch.

6 · Region specs

6.1 Action slots plugin components

  • Placement. A slot zone in the right control group, before the mic; voice and submit/queue/stop always render after it, untouchable. Order across plugins follows composition order.
  • Chrome. Plugins vendor the documented PromptIconButton recipe (BB registry) for native-matching size, coarse-pointer targets, and tooltip behavior — or render anything else at their own visual risk. The host constrains the slot to the action-row height so a misbehaving component cannot distort the composer's geometry.
  • Compact layout renders only the submit/stop control today; plugin action slots are not mounted there (same suppression as accessories). Components can adapt short of that via useComposerView().layout.
  • Isolation. Each slot is its own PluginSlotMount; a crash collapses that button alone, remounting on the next plugin generation.

6.2 Plus menu host-rendered data

  • Placement. After the native items (Attach files · Skills · Plan · Goal · Automation), behind a separator; with ≥2 contributing plugins, each plugin's items get a group header (plugin display name).
  • Behavior. run receives the bound composer API + view snapshot. Selection reuses the native selectedItemRef close path, so the caret lands wherever run put it; dismissal restores focus like native items. Errors toast + log.
  • Compact layout has no + trigger; items are unavailable there by construction (documented, no error).

6.3 Banner slots plugin components · host chrome

  • Placement. A plugin row in the existing stack, below native cards and immediately above the composer. Ordered by (pluginId, registration order, array order).
  • Chrome. Default "card" wraps the component in PromptStackCard (border, radius, raised surface, labeled section) so plugin cards match "Running background command"; "bare" opts out while staying inside the measured stack.
  • Layout physics for free. The stack already measures itself (useLayoutEffect + ResizeObserver) and feeds height compensation, so plugin banners participate in scroll anchoring and narrow layouts with zero plugin code — no portals, MutationObserver, closest(), or host class names. This deletes the Omegacode workaround outright.
  • Visibility & cleanup. Render null to hide (row collapses). Scope filtering via scopes; mounts key on (pluginId, generation, scope), so scope changes and reloads remount cleanly.

6.4 Text effects the one non-React surface

ProseMirror owns the editor's text nodes, so range paint cannot be a component — it goes through one host-owned decoration engine with two sources:

  • Content-derived rules (richText.effects) — the ultracode-highlight pattern made public: match(text) returns plain-text ranges (mentions count as their text form), recomputed on edits, painted with the rule's className. Match ⇒ paint, never mutate: serialization, mentions, attachments, paste, undo/redo, selection, and plain-text mode are structurally safe. A throwing match() disables that rule for the generation.
  • State-derived paint — setTextEffect({ className }) for anything driven by plugin state (an in-flight improve call, an RPC event). Ranges aren't needed here in v1: it paints the whole draft, like today's shimmer.

Styling. The class comes from the plugin's own bundled CSS — animations, gradients, colors included. Paint-only is a documented convention, not an enforced rule; violating it (metric changes) makes the caret jump in that plugin's own feature while the document and host structure remain untouchable. A small set of theme tokens (--ink, --canvas, --accent, …) is documented as public SDK API so effects follow custom palettes.

Dogfooding guarantee. PromptUltracodeHighlightExtension and PromptTextEffectExtension are deleted and re-registered as host sources on this engine — one code path, and proof the public shape needs no privileged escape hatch. Host sources paint first, then plugins in composition order; overlapping paint stacks.

v2 candidates, explicitly deferred: ranged imperative effects, match-and-transform input rules (text-to-text rewrites applied by the host as proper editor transactions), semantic inline renderers, paste transformers. Each is additive.

7 · Composition, lifecycle, isolation

ConcernRule
OrderPlugins by pluginId asc → registrations in call order → entries in array order. Deterministic across reloads.
Registryplugin-slots.ts snapshot grows composerCustomizations with the same wholesale-replace + generation semantics; per-entry validation at interpretation (id shape, duplicate ids, scope names) rejects invalid entries individually with a logged reason.
Crash containmentAction/banner components crash inside their own boundary; menu run and rule match errors are caught, logged, and disable only that entry. The native composer never degrades.
Effect & lock lifetimesetTextEffect, setInputLock, and setThreadRowStatus are scoped to the calling slot's plugin + composer instance and auto-clear on unmount, scope change, reload, and disable — a crashed plugin cannot leave the composer painted or locked.
Scope changeNew scope = new mount keys: slots remount, effects/locks clear, useComposerView() reflects the new instance.
pendingInteractionSuspends action slots, menu items, and decoration rules along with the editor it replaces; banners stay mounted.
Unsupported regionsA registration targeting a surface without that region (e.g. + menu in compact) is silently skipped there, with a one-time dev-mode console note.

10 · Test plan (focused, per repo guidelines)

  • Registration/validation — duplicate ids rejected individually, invalid scope names, wholesale replace on reload never duplicates, deterministic cross-plugin order.
  • Action slots — mount/order in the right group, crash isolation per slot, height containment, not mounted in compact, native voice/submit untouched (extending PromptBoxInternal.test.tsx).
  • Input lock — editor read-only + aria-busy while locked; auto-release on unlock, unmount, scope change, and plugin reload; submit/stop still reachable.
  • Plus menu — plugin section ordering + separators, focus restoration parity with native items, disabled callback, run error containment.
  • Banners — card vs bare chrome, null-render collapse, crash isolation per card, stack height measurement including plugin rows, scope-change remount cleanup.
  • Text effects — decorations across rich/plain modes, offsets correct around mentions, serialization byte-identical with rules active, classes applied/removed across edits and remounts, shimmer/ultracode parity as host-registered sources, throwing match() disabled.
  • Cross-cutting — two plugins composing without interference, pendingInteraction suspension, testing-harness capture snapshots.

11 · Open questions for review

1 · Slot geometry enforcement
The host constrains action slots to the action-row height; should it also cap width (e.g. max-width per slot) so a runaway component can't push voice/submit off-row, or is the boundary + docs recipe enough?
2 · Left-footer region
v1 maps legacy accessories to a frozen footer slot but offers no new API for it. Keep frozen (push everything to actions/menu/banners), or expose footer as a first-class slot?
3 · Ranged imperative effects
setTextEffect paints the whole draft in v1 (parity with today's shimmer). Add range support now, or wait for a motivating plugin?
4 · Input rules in v1?
Match-and-transform stays v2. Pull forward if a plugin needs live text rewriting rather than paint.
