Amends SPEC 05 (adds a development tier below the verification tiers) and SPEC 06 (adds ACTION-class tools). Derived from a feature-level teardown of Embedder's shipping product, August 2026.*

**Spec set:** 00 Foundation · 01 Sync Engine · 02 Findings & VEX Triage · 03 Product Security · 04 Bill of Materials · 05 Firmware, Bench & Documents · 06 Agentic Surfaces · 07 KiCad & the Hardware Design Plane · **08 Firmware Authoring (this)**

## 1. The gap this closes

**Everything in SPECs 00–07 runs in the read direction.** We analyze firmware, triage its findings, model its threats, prove its requirements, read its bill of materials, and now read its schematic. We have built an extraordinary apparatus for evaluating a product that already exists.

**We have no surface for writing one.**

That is the gap Embedder occupies, and the reason it matters isn't competitive — it's that the Eagle thesis is *design → develop → manufacture as one loop*. A loop with no authoring step isn't a loop. The Golden Loop in SPEC 06 has the agent "implement the fix in the firmware source" as beat 11, and that beat is currently hand-waved: it assumes a generic coding agent with no hardware grounding, no build, no flash, no serial, and no way to know whether the thing it wrote actually runs on the board.

**What this spec adds:** the loop from *requirement* to *running, instrumented firmware on real silicon* — grounded in the datasheets and the schematic, gated by citations, and coupled to the verification and security layers we already have.

**The strategic point, stated once.** [HardSecBench](https://arxiv.org/html/2601.13864v1) found that LLM-generated firmware frequently passes functional checks while embedding security defects. Generation without an analysis layer ships vulnerabilities. Embedder generates. We generate **and prove** — because the proving half already exists in SPECs 02–05. That coupling is not a feature we add to a code generator; it is the reason ours is worth using.

### 3.1 On the user's hypothesis — skills, workflows, plugins

Mostly right, with one correction worth making explicit.

**Skills encode method. They do not encode capability.** A skill can teach an agent the Observe → Hypothesize → Probe → Verify loop, when to reach for a logic analyzer versus a scope, and that an uncited register value must be quarantined. It cannot open a USB device, speak SCPI, or drive GDB. Those need real tools underneath.

This is not a quibble — it's the central design finding, and there is evidence for it. [IoT-SkillsBench](https://arxiv.org/abs/2603.19583) (3 platforms, 23 peripherals, 42 tasks, 378 hardware-validated experiments) found that agents with **human-expert-authored skills achieve near-perfect success**, while the same agents with LLM-self-generated skills — or none — fall materially short, because "code that compiles may still fail on real devices due to timing constraints, peripheral initialization requirements, or hardware-specific behaviors."

So: **the skills are load-bearing, and they need real tools beneath them.** Both halves matter. Build the tools, then write the skills carefully, by hand, from people who have actually brought up hardware.

The split for this spec:

| Layer | What goes there |
|---|---|
| **Plugin surfaces** (panels, RPC, cache) | Grounding index · citation store · bench/instrument registry · serial console · probe-script library |
| **Agent tools** | `fs_ground_query` · `fs_build` · `fs_flash` · `fs_serial` · `fs_probe` · `fs_hw_status` |
| **Skills** | The debug loop · citation discipline · driver-authoring method · porting playbooks · instrument selection |
| **Workflows** | Bring-up · port · debug-on-bench · HIL-test-authoring — each a named, resumable sequence |

## 4. The surface

One nav panel, `firmware`, with three tabs. Plus a **Debug mode** that is a thread-level state, not a panel.

### 4.1 An amendment to SPEC 05 first — development tier vs. verification tier

SPEC 05's bench answers *"does this build pass?"* Debug mode answers *"why is this hanging?"* **Those are different loops with different safety postures**, and conflating them is a design error.

The bench gains a **tier D (development)** below tier 0:

| Tier | Question | Trigger | Safety |
|---|---|---|---|
| **D — development** | Why is this behaving this way? | Interactive, human-initiated | Read-mostly; destructive ops need explicit instruction |
| 0 — static | Does it build and pass analysis? | Every commit | Safe |
| 1 — emulation | Does it behave under rehosting? | Per PR | Sandboxed |
| 2 — determinism | Is timing stable? | Nightly | Sandboxed |
| 3 — HIL | Does it work on silicon? | Pre-release | Gated |
| 4 — chamber/lab | Does it certify? | Release | Manual |

Tier D results are **diagnostic, not evidentiary** — they never feed the requirement × tier matrix and never produce attestations. A hypothesis confirmed at the bench is a finding, not a proof. Keeping that boundary sharp is what stops the evidence chain from being polluted by exploratory work.

### 4.2 Tab 1 — Grounding (`/firmware/grounding`)

The documentation-as-RAM layer. **This is the highest-leverage thing in this spec** and the piece with the longest lead time, so it is phase one.

**What it holds.** Per project: the platform (MCU family), its reference manual, SVD device file, errata, and app notes; each peripheral with its datasheet; the SDK/HAL sources; and — the part nobody else can replicate — **the reverse-engineered corpus of shipped firmware for comparable devices.**

Embedder grounds in what the vendor *says*. We can additionally ground in what shipped firmware *does*: undocumented registers, init sequences that actually work, vendor SDK bugs, real driver structure. That corpus is the largest outside the silicon vendors and it is the difference between a datasheet-faithful driver and one that works.

**UI.** Sources list with indexing status and coverage; a part picker that mirrors `/peripheral` (search a catalog, or add a custom part by uploading PDFs); per-source citation counts; a "what does this ground?" view showing which generated values trace to which document.

**Retrieval.** Chunk-and-embed with structure preservation — register tables, pin tables, and timing diagrams are not prose and must not be chunked as prose. Queries return **passages with document, page, and table coordinates**, because a citation that can't be clicked back to a page isn't a citation.

**Reuses SPEC 05 Part C** for document storage and SPEC 04's extraction machinery. Do not build a second document store.

### 4.2.1 Seeding the catalog from open sources

We are not going to out-breadth a company whose whole product is a 500-MCU catalog, and we shouldn't try (§9.2). But **breadth and depth are not the same acquisition problem**, and a surprising amount of breadth is available as structured, permissively-licensed data rather than as PDFs.

**The distinction that makes this tractable:** Embedder's catalog is *documents indexed for retrieval*. Much of what an agent actually needs at register level already exists as **machine-readable descriptions** — no PDF parsing, no extraction confidence, no citation ambiguity. A register address from an SVD file is not "extracted with confidence 0.9"; it is **declared by the vendor**, and it belongs at the same provenance tier as `kicad_bom` (SPEC 07 §7.1).

| Source | What it gives | Coverage | License | Fit |
|---|---|---|---|---|
| **CMSIS-SVD** (`cmsis-svd/cmsis-svd-data`) | Peripheral register maps, bit fields, reset values, interrupt numbers — **the exact data driver code needs** | Aggregated from silicon vendors, organized by vendor | **Per-vendor licenses included in-tree**; tooling Apache-2.0 | **Highest value. Start here** |
| **Open-CMSIS-Pack DFPs** | Device family packs: startup/system files, headers, flash algorithms, memory maps, board support | Broad across ARM vendors | Per-vendor | High — memory maps and flash algorithms are hard to get elsewhere |
| **Zephyr devicetree bindings** | YAML bindings per peripheral and SoC, plus board definitions | Very broad, actively maintained | Apache-2.0 | High — and it's *semantic*, not just register-level |
| **Linux devicetree bindings** | YAML schemas for thousands of peripherals | Broadest for application-class SoCs | GPL-2.0 / dual | High for the **router/Linux** side, which is our actual PoC target |
| **probe-rs target descriptions** | Flash algorithms, memory regions per chip | Wide MCU coverage | Apache-2.0 / MIT | Medium — directly useful for flash/debug |
| **OpenOCD target configs** | Debug/flash configuration per target | Wide | GPL-2.0 | Medium |
| **PlatformIO board manifests** | Board-level JSON: MCU, flash/RAM, upload protocol, frameworks | ~1000+ boards | Apache-2.0 | Medium — board-level, not register-level |
| **Embedded Rust PACs / `svd2rust`** | SVD-derived typed peripheral APIs | Follows SVD coverage | MIT/Apache | Low direct, useful as validation |
| Datasheet aggregator sites | PDFs | Broad | **Hostile to scraping; licensing unclear** | **Avoid** |
| Distributor APIs (DigiKey, Mouser, Nexar/Octopart) | Parametric attributes + datasheet links | Very broad | Commercial ToS | Medium — better for **HBOM (SPEC 04)** than for register grounding |

**The plan that falls out of this:**

1. **Ingest CMSIS-SVD first.** It is the single highest-value corpus and it is structured. Register maps, bit fields, and reset values become citable facts with vendor provenance, not extraction guesses.
2. **Add Zephyr and Linux devicetree bindings** for semantic peripheral knowledge — what a peripheral *is* and how it's configured, which SVD doesn't carry. Linux bindings matter disproportionately because the router PoC is application-class Linux, not Cortex-M.
3. **Layer Open-CMSIS-Pack DFPs** for memory maps and flash algorithms.
4. **Keep PDFs for depth on the parts Eagle actually ships** — errata and timing diagrams are where the PDF is irreplaceable, and where per-part curation earns its cost.

**Add a provenance tier for this.** Structured vendor data sits above document extraction and beside `kicad_bom`:

| Provenance | Confidence | Meaning |
|---|---|---|
| `svd` / `dfp` / `devicetree` | **1.0** | **Declared by the vendor in machine-readable form** |
| `kicad_bom` | 1.0 | Asserted by the design (SPEC 07) |
| `human` | 1.0 | Someone typed it |
| `re_corpus` | 0.85 | Observed in shipped firmware — *what actually works*, which sometimes contradicts the datasheet |
| `document` | ~0.72 | An agent read a PDF and proposed it |

**Licensing is the one thing to get right before ingesting.** CMSIS-SVD ships per-vendor licenses in-tree and they are not uniform; Linux bindings are GPL-family; distributor APIs have commercial terms. **Track license per source in `ground_source`** and make it queryable, because "which of our grounding data can ship in an air-gapped customer deployment" is a question someone will ask, and the honest answer needs to be computable rather than remembered.

```sql
ALTER TABLE ground_source ADD COLUMN license TEXT;         -- SPDX id where possible
ALTER TABLE ground_source ADD COLUMN redistributable INTEGER NOT NULL DEFAULT 0;
```

**Effort: ~4 days for SVD + devicetree ingest**, which buys most of the structured breadth. That is a genuinely good trade against curating hundreds of PDFs, and it is additive to the depth strategy rather than a substitute for it.

### 4.3 Tab 2 — Authoring (`/firmware/authoring`)

Where a requirement becomes code, with its receipts attached.

**Citation gating is the core mechanic and it is not optional.** Every generated hardware-touching constant — register address, bit field, timing value, clock divider, pin assignment — must carry a citation to a document, a schematic net, or the RE corpus. **An uncited value is not written; it is quarantined into a review queue.**

```yaml
# .fs/authoring/citations/<file>.yaml   — OVERLAY, git-tracked, reviewable
version: 1
file: src/drivers/bme280.c
values:
  - symbol: BME280_I2C_ADDR
    value: "0x76"
    citation: { doc: "BME280-DS002.pdf", page: 32, table: "6.2" }
    confidence: 1.0
  - symbol: I2C1_SCL_PIN
    value: "PB6"
    citation: { source: "kicad", ref: "U2", net: "I2C1_SCL", sheet: "sensors.kicad_sch" }
    confidence: 1.0
  - symbol: BME280_STARTUP_DELAY_MS
    value: "2"
    citation: null
    status: quarantined            # ← blocks the write, opens a review item
    note: "Inferred from typical startup times; not found in datasheet"
```

Note the second entry: **the pin assignment cites the schematic, via SPEC 07.** That join — code grounded in the board as built rather than the vendor dev kit — is the thing Embedder does well and we can now do better, because our schematic is already linked to the BOM, the CVEs, and the threat model.

**The authoring panel** shows generated files with per-value citation coverage as a gutter annotation (cited / inferred / quarantined), the review queue for quarantined values, and a diff view where accepting a value writes it and records the acceptance.

**Workflows**, each a named resumable sequence rather than a prompt someone remembers:

| Workflow | Shape |
|---|---|
| **Bring-up** | Part + bus + pins → datasheet research → cited plan → driver + init → build → flash → serial verify → HIL test |
| **Port** | Source and target platforms → capability diff → mapping table → staged migration with build gates |
| **Requirement→code** | An EARS requirement (SPEC 03) → implementation → the verification contract that proves it |
| **Debug-on-bench** | The §4.4 loop |

**Spec-first, always.** The plan is cited and human-approved before code exists. This matches SPEC 01's `plan`/`push` idiom, and it is the same product principle in a new domain: *the agent proposes, the human approves, and the diff is the artifact.*

### 4.4 Tab 3 — Bench & Instruments (`/firmware/bench`)

**Device registry.** `fs_hw_status` enumerates connected instruments — debug probes, logic analyzers, power analyzers, scopes, serial ports — with make, model, connection, and claim state. Rendered as a live device panel.

**The serial console** is a first-class surface: integrated, auto-connecting after flash, with regex filtering, and readable by the agent. A `~`-prefixed send path for AT commands and device CLIs. This is unglamorous and it is used more than anything else in this spec.

**Probe scripts, not opaque tool calls.** Following Embedder's best structural idea: the agent **writes a Python probe script to `.fs/bench/probes/`, and then runs it.** The script is inspectable, editable, reusable, diffable, and committable. A probe that found a bug once becomes a regression test. An opaque `capture_i2c()` tool call is gone the moment it returns.

**The debug loop as a skill.** Observe → Hypothesize → Probe → Verify, written by hand:

1. **Observe** — `fs_hw_status`, recent serial/RTT, current GDB state, the source in question
2. **Hypothesize** — enumerate candidate root causes, **ranked by likelihood × ease of verification**
3. **Probe** — write and run the smallest script that discriminates between hypotheses
4. **Verify** — check results against each hypothesis; narrow, or report the root cause with its evidence

The ranking step is the part that separates a good debugging agent from one that flails, and it is exactly the kind of judgment that belongs in a hand-written skill rather than in tool code.

**Safety rails, copied wholesale because they are correct:**

- **Non-destructive by default.** Flash, reset, erase, and fuse programming require explicit human instruction — never inferred from intent
- **Rate-limited hardware I/O**
- **Instrument arbitration** — one claimant per device, with a claim/release protocol, so parallel agents cannot fight over a JTAG probe
- **Helper libraries installed on first use with confirmation**, not silently
- **Debug mode is a distinct thread state.** Instrument tools do not exist outside it

### 4.4.1 The instrument bridge — what to actually build on

**There are two different benches here, and conflating them is the mistake to avoid.**

| | **The debug bench** (tier D3) | **The production bench** (ATE) |
|---|---|---|
| Question | Why is this firmware misbehaving? | Does this unit pass? |
| Instruments | Debug probe, logic analyzer, power profiler, scope | PSU, DMM, electronic load, DAQ, PLC, Modbus |
| Scale | One engineer, one board | Millions of units, a line |
| Whose territory | Embedder's | **Nobody's — and it's Eagle's #1 ask** |

The candidate libraries sort cleanly across those two, which makes the choice easier than it first appears.

| Option | What it is | Verdict |
|---|---|---|
| **`instro`** (Nominal, Apache-2.0) | Typed Python API over test-and-measurement instruments by **category**: `InstroPSU`, `InstroDMM`, `InstroELoad`, `InstroDAQ`, `I2CInterface`, `ModbusDevice`, plus experimental `InstroScope` and EtherNet/IP for CompactLogix-class PLCs. Vendors: B&K, Keysight, Rigol, Siglent, TDK Lambda, Keithley, NI-DAQmx, LabJack, MCC, Total Phase. Ships a **built-in SCPI simulation server** | **Adopt — for the production bench.** Actively released (latest Jun 2026). See the three reasons below |
| **PyVISA** | The universal SCPI/GPIB/serial/USB/ethernet transport layer; `pyvisa-py` is a pure-Python backend | **The floor.** Everything else sits on it. Mature and ubiquitous |
| **PyMeasure** | Object-oriented instrument drivers on top of PyVISA, hiding raw SCPI; large ready-made driver set | **Adopt for breadth** where `instro` has no category |
| **Vendor SDKs** | `logic2-automation` (Saleae), `dwfpy` (Digilent), `ppk2-api` (Nordic), `joulescope`, PicoScope SDK, J-Link/OpenOCD | **Primary for the debug bench.** `instro` covers none of these categories |
| **Labgrid** (Pengutronix) | Board-farm control — power, reset, serial, USB bootstrap, remote board booking | **Adopt as the tier-3 board spine.** Board control, not instrument control |
| **sigrok / libsigrok** | 258 devices under one C API plus protocol decoders | **Optional long-tail adapter.** Last stable release is 0.5.2, **December 2019** — do not make it load-bearing |
| **QCoDeS** | Mature instrument + data-management framework from the quantum-computing consortium | **Skip.** Excellent, but its data-management opinions are shaped for physics labs |

**Three reasons `instro` is the right pick for the production bench:**

1. **Its category coverage is the ATE stack, not the debug stack.** PSU, DMM, electronic load, DAQ, Modbus, EtherNet/IP to CompactLogix PLCs — that is a manufacturing test rig, described precisely. It has no logic analyzer, no power profiler, no debug probe, and its scope support is explicitly `unstable`. That isn't a shortcoming; it's a different target. **And it happens to be the target Eagle actually asked for** — "how do we build our own test systems after we have our own line" was the stated goal of the August 12 session.
2. **The simulation server.** `python -m instro.psu.scpi_sim_server` gives a simulated PSU with no hardware attached. That makes bench code developable and CI-testable without a rig — the same mock-first discipline the implementation plan uses to keep lanes parallel, applied to hardware.
3. **It already ships the agentic pattern we specced.** The repo carries `.claude/`, `.agents/`, and `.codex/` skills — **`add-instrument-driver`**, which scaffolds a vendor driver from a programming manual, and **`validate-driver-hardware`**, which smoke-tests an authored driver against the real instrument and self-corrects. That is §4.3's citation-grounded authoring loop and the D3 verify step, applied to instrument drivers instead of firmware drivers. **Copy the pattern wholesale**; it is independent evidence that the approach works.

**Be clear-eyed about the risk.** `instro` is very young — single-digit stars, three contributors, nine releases. The publishing path leads to Nominal Core, their commercial platform, so expect gravity in that direction. Mitigation is structural: put it behind our own `InstrumentDriver` interface like everything else, use it for categories where it's strongest, and keep PyVISA/PyMeasure as the escape hatch. The Apache-2.0 license means a fork is always available if the project stalls or the commercial pull becomes uncomfortable.

**Recommendation:** PyVISA as the transport floor · **`instro` for the production/characterization bench** · vendor SDKs for the four debug-bench instruments · PyMeasure for long-tail SCPI gear · Labgrid as the tier-3 board spine · sigrok optional. One `InstrumentDriver` interface over all of it, so the choice stays an implementation detail. Python throughout is not a problem — probe scripts are Python by design (§4.4).

**Phasing, by honest value:**

| Phase | Instruments | Transport | Bench | Why |
|---|---|---|---|---|
| 1 | GDB (J-Link/OpenOCD), serial/RTT | native | debug | Covers most debugging; lowest cost |
| 2 | Logic analyzer (Saleae, Digilent) | vendor SDK | debug | Bus-level truth; protocol decode |
| 3 | Power profiler (PPK2, Joulescope) | vendor SDK | debug | Sleep-current regressions are a top defect class |
| 4 | PSU, DMM, electronic load, DAQ | **`instro`** | production | Characterization; the on-ramp to Eagle's line |
| 5 | Scope (PicoScope USB, Siglent LAN) | SDK / SCPI | both | Analog integrity |

### 4.5 The cascading debug model — where we beat Embedder

Embedder's debug mode reaches for physical instruments. **That's the right capability and the wrong default.**

We have three tiers of investigation that cost nothing and that Embedder structurally cannot use: static analysis of the binary (STP), rehosted emulation (SPEC 05 tier 1), and deterministic replay (Renode). **The cascade principle: answer the question at the cheapest tier that can actually answer it, and escalate only when the tier below genuinely cannot.**

| Tier | Question it answers | Cost | Latency | What we bring |
|---|---|---|---|---|
| **D0 — static** | What does the code *say* it does? | free | seconds | **STP disassembly and callgraph** — we can read the vendor blob Embedder can't see. Plus the **RE corpus**: how do 500 shipped devices initialize this peripheral? |
| **D1 — rehosted** | Does it reproduce without hardware? | free | minutes | FirmAE/EMBA-lineage rehosting driven by our own unpacker. If it hangs in QEMU, you never touch the bench |
| **D2 — deterministic** | Is it byte-identically reproducible? | free | minutes | Renode for the boot chain and golden regressions. Bisect against a deterministic replay instead of a flaky board |
| **D3 — physical** | Does it happen on real silicon? | rig | minutes–hours | GDB, logic analyzer, power analyzer, scope. **Where Embedder starts** |

**The agent should be taught to walk this ladder**, and that reasoning belongs in the `fs-debug-bench` skill:

> Before reaching for an instrument, ask what tier can answer the question. A hang with a known call path is a D0 question. A hang you can reproduce in emulation is a D1 question. Escalate when the tier below returns *inconclusive*, not when it returns *inconvenient*.

**Why this is genuinely better, not just cheaper.** Physical debugging is serialized on scarce hardware, it perturbs the system under observation, and it produces results that are hard to reproduce. D0–D2 are parallel, non-perturbing, and reproducible. An engineer who can bisect a boot failure against a deterministic Renode replay is in a strictly better position than one power-cycling a board — and our RE corpus means D0 can often answer *"is this init sequence wrong?"* outright, by comparison against firmware known to work on the same silicon.

**The honest limit, which matters more than the pitch.** Some defect classes are **only** visible at D3, and the skill must say so explicitly rather than letting the agent burn hours in emulation:

- analog integrity, signal quality, rail droop, EMI
- real timing, interrupt latency, DMA races under true clocks
- actual sleep current and boot energy
- radio behavior, thermal, and anything mechanical
- **silicon errata** — the gap between what the chip is documented to do and what it does

And a failure mode to design against: **over-trusting emulation.** Rehosting achieves high boot rates, but *boots* is not *behaves identically* — emulated timing is not real timing. So the ladder has a hard rule: **a D1/D2 result may refute a hypothesis, but it may not confirm a timing-, power-, or analog-class hypothesis.** Those escalate regardless of what emulation says. Encode that as a check in the skill, not as folklore.

**On Renode specifically** — the Verification Bench assessment landed on: automated rehosting is the primary digital-twin path; **Renode is a deterministic scalpel for boot/secure-boot and golden regressions**, not a general-purpose emulation strategy, because hand-writing platform models for a modern SoC is a months-long job. That conclusion holds here. In the cascade, Renode earns tier D2 precisely because determinism is what bisection needs — and it stays narrow.

**This is the strongest single differentiator in SPEC 08.** Embedder can only debug what it can physically instrument. We can debug statically, in emulation, deterministically, *and* physically — and we can see inside the vendor blobs at every tier. Their tool needs the board on the desk. Ours needs it only for the questions that genuinely require silicon.

## 5.1 Integrating the structured catalog

*Added after building the catalog (see `Catalog Pipeline/`). The §5 schema above is document-shaped — `pages`, `path` into a document store, `embedding BLOB`. The structured catalog is a different animal and needs its own treatment.*

**The measured artifact:** 209 devices, **2,483,791 facts**, zero parse failures, from eight vendors' CMSIS-SVD data. Every fact is vendor-declared at confidence 1.0.

### Two grounding planes, not one

| | **Plane A — the catalog** | **Plane B — project documents** |
|---|---|---|
| Content | Structured vendor descriptions (SVD, DFP, devicetree) | Datasheets, errata, app notes, schematic exports |
| Shape | Identifiers and numbers | Prose, tables, timing diagrams |
| Query | **Exact / prefix lookup + full-text** | **Embedding similarity** |
| Mutability | **Read-only, versioned artifact** | Per-project, user-added |
| Confidence | **1.0 — declared** | ~0.72 — extracted |
| Scale | 2.5M facts, grows with vendors | Tens of documents per project |

`fs_ground_query` federates both and **labels every result with its plane**, so the confidence ladder stays legible to the agent and to whoever reviews the citation.

### The decision that matters: no embeddings for structured facts

**A register lookup is an exact-match query, not a similarity query.** `STM32H753.USART1.CR1.UE` is an identifier.

Embedding 2.5M short strings would be expensive, slow, and — the actual problem — **actively harmful**. Nearest-neighbour over `USART1.CR1.UE` and `USART2.CR1.UE` returns near-misses that are indistinguishable from hits, which is precisely the failure mode that produces a confidently wrong base address in generated code. Citation gating catches an *uncited* value; it does not catch a value cited to the wrong peripheral.

So the catalog uses **B-tree indices for identifier lookup and FTS5 for descriptive text**, and nothing else:

```sql
-- catalog.db — READ-ONLY, shipped/cached separately from the plugin's data.db
CREATE TABLE cat_device (
  device_id   TEXT PRIMARY KEY,        -- 'stmicro/STM32H753x'
  vendor TEXT NOT NULL, name TEXT NOT NULL,
  cpu TEXT, width INTEGER,             -- width is the fallback for register.size
  description TEXT,
  source_id TEXT NOT NULL
);

CREATE TABLE cat_fact (
  fact_id    INTEGER PRIMARY KEY,
  device_id  TEXT NOT NULL,
  kind       TEXT NOT NULL,            -- peripheral|interrupt|register|field
  peripheral TEXT, register TEXT, field TEXT,
  addr       TEXT,                     -- base address or offset, hex string
  bit_offset INTEGER, bit_width INTEGER,
  access     TEXT, reset_value TEXT,
  description TEXT,
  source_id  TEXT NOT NULL,
  source_file TEXT NOT NULL            -- the exact .svd — this IS the citation
);

-- identifier lookup: the primary path
CREATE INDEX ix_fact_path ON cat_fact (device_id, peripheral, register, field);
CREATE INDEX ix_fact_periph ON cat_fact (peripheral, register);

-- descriptive search: the secondary path
CREATE VIRTUAL TABLE cat_fact_fts USING fts5(
  description, peripheral, register, field,
  content='cat_fact', content_rowid='fact_id'
);

CREATE TABLE cat_source (
  source_id TEXT PRIMARY KEY, vendor TEXT NOT NULL, kind TEXT NOT NULL,
  origin TEXT, license TEXT, redistributable INTEGER NOT NULL DEFAULT 0,
  catalog_version TEXT NOT NULL
);
```

2.5M rows is unremarkable for SQLite. Indexed lookup is sub-millisecond; FTS5 handles the descriptive path.

### A separate database file, and why

`catalog.db` lives beside the plugin's `data.db`, not inside it:

- It is a **build artifact**, not user state — rebuilding it must never touch user data, and migrating user data must never rebuild it
- Opened **read-only** (`mode=ro`), so it can't be corrupted by the plugin and doesn't participate in `bb.storage.migrate`'s append-only chain
- **Versioned and cacheable** independently: `catalog.db` for `catalog_version` 2026.08.1 is immutable and safe to fetch once
- Gitignored and re-fetchable, like the firmware mount

### Distribution — and the licensing flag becomes a build filter

This is where §9.2's licensing work stops being advisory and starts doing something.

The measured reality: of the eight vendors built, **only Raspberry Pi is redistributable** (BSD-3-Clause). STMicro ships a vendor EULA; six ship no license at all. Absence is not permission.

**So the catalog builds in two flavours:**

```bash
build_catalog.py build --redistributable-only    # → shippable; only permissive sources
build_catalog.py build                            # → full; local use only
```

- **The shipped catalog** contains only sources with `redistributable: true`. It's a release artifact, fetched on first use into the plugin data dir, cached by `catalog_version`.
- **The full catalog** is built locally by the user from their own `fetch`. Same schema, same code path, superset of facts. The plugin opens whichever is present and reports coverage honestly in the Grounding tab.

That turns the license column into an enforced boundary rather than a note somebody has to remember. It also means the demo can ship with real grounding without anyone having to make a licensing judgement call under time pressure.

**Open item:** the on-disk size of `catalog.db` at 2.5M facts hasn't been measured. If it lands above a few hundred MB, the fetch-on-first-use path needs progress reporting and resumability — mechanics SPEC 05's firmware mount already has and can lend. **Measure before designing around it.**

### Query surface

```ts
// Structured path — exact, and the citation is the SVD file itself
fs_ground_query({ device: "nrf52840", peripheral: "UARTE0" })
// → { plane: "catalog", confidence: 1.0,
//     facts: [{ kind: "peripheral", addr: "0x40002000",
//               citation: { source_file: "Nordic/nrf52840.svd", vendor: "Nordic" } }] }

// Descriptive path — FTS, still exact citations
fs_ground_query({ text: "single-cycle IO", device: "RP2040" })
```

**Two rules for the retrieval layer**, both learned from the built data:

1. **`register.size` is frequently `null`** — correct SVD behaviour, meaning the register inherits `cat_device.width`. Resolve the fallback at query time. Treating null as unknown drops widths on a large fraction of registers.
2. **Never return a catalog fact without its `source_file`.** The whole value of plane A is that the citation is a vendor file and a precise path, not a page number and a confidence score.

## 6. bb integration

### Agent tools

| Tool | Class | Notes |
|---|---|---|
| `fs_ground_query` | read | Returns **cited passages** with doc/page/anchor — never raw chunks |
| `fs_ground_add` | write | Registers a document for indexing; writes local metadata only |
| `fs_cite_write` | write | Writes citation overlay YAML. **Quarantines uncited values** |
| `fs_hw_status` | read | Enumerates instruments and claim state |
| `fs_build` | **action** | Runs the project build. Local subprocess |
| `fs_flash` | **action** | **Destructive. Requires explicit human instruction in-turn** |
| `fs_serial` | **action** | Read, and send behind a confirmation |
| `fs_probe` | **action** | Runs a probe script from `.fs/bench/probes/` against claimed devices |

**Five new ACTION-class tools — and this needs a decision, not a shrug.** SPEC 06 §5.3 enumerated three; SPEC 07 added a fourth. This spec proposes five more, which takes the allowlist to nine and materially changes the safety posture.

The distinction that holds: **all of them invoke local subprocesses or local hardware; none mutates Assurance Studio.** The model-mutation boundary is intact. But `fs_flash` genuinely can brick a device, and no amount of allowlist bookkeeping changes that.

**So `fs_flash` gets a stronger rule than allowlisting**: it requires an explicit human instruction *in the current turn*, and intent inferred from a plan does not count. This mirrors Embedder's own rule and it is the correct one. It should be written as a test, not a convention.

### Directives
`::fs-citation{file,symbol}` — a value with its source, clickable back to the page · `::fs-probe{id}` — probe result with captures · `::fs-serial{lines}` — a serial excerpt · `::fs-build{id}` — build result with the diagnostic that matters.

### Skills — the load-bearing part

| Skill | Teaches |
|---|---|
| `fs-bringup` | Bring-up method: research before code, cite every constant, verify on serial before declaring done |
| `fs-debug-bench` | Observe → Hypothesize → Probe → Verify; **ranking hypotheses by likelihood × ease of verification**; instrument selection |
| `fs-citation` | Never emit an uncited hardware constant. Quarantine and ask |
| `fs-porting` | Platform migration playbooks; capability diffing; staged gates |

**These get written by hand, by people who have brought up hardware.** IoT-SkillsBench is unambiguous that self-generated skills underperform, and this is the one place in the build where the quality of the prose *is* the quality of the product.

## 7. What we deliberately do not do

- **No fine-tuned model.** Embedder scaffolds frontier models and says so; the defensibility is in grounding and verification, not weights.
- **No safety-certification claims.** No qualified AI toolchain exists for ISO 26262, DO-178C, or IEC 62304. Every vendor's compliance language here — Embedder's included — is rule-checking plus metadata. We run the checks; we do not claim qualification.
- **No autonomous end-to-end product firmware.** Nobody has demonstrated agentic assembly of bootloader → BSP → RTOS → connectivity → app without deep human scaffolding. The honest envelope is *subsystem on a custom board with generated HIL tests*, and that is worth a lot.
- **No pretending citation gating solves hallucination.** It fixes wrong *constants*. It does not fix wrong *dynamics* — timing, interrupts, DMA, power-state corners remain the published failure class. Which is precisely why tier D and the HIL loop exist.

## 9. Decisions

*Resolved 12 Aug 2026. Each item states the decision and what it changes.*

### 9.1 RE-corpus — **proceed, managed carefully** ✅

We believe we have legal standing to ground generation in the reverse-engineered firmware corpus. Phase 8n proceeds.

**What this changes:** 8n stays in the plan and keeps its long lead time, so it starts early. Because "managed carefully" has to mean something operationally, the corpus gets three controls rather than a policy note: **per-source licensing and permission recorded in `ground_source`** (§4.2.1) · **provenance stamped on every corpus-derived value** so a generated constant can always be traced to what it was learned from · **a scope filter** so corpus grounding can be restricted per deployment. That last one is what makes the answer to "was my firmware used to help a competitor" computable rather than reassuring.

### 9.2 Catalog — **depth on Eagle's parts, plus an open structured seed** ✅

Depth is the strategy. But breadth and depth turned out to be different acquisition problems, and much of the breadth is available as **structured, permissively-licensed data rather than PDFs** — see the new **§4.2.1**.

**What this changes:** a new **phase 8a+** ingests CMSIS-SVD, Zephyr and Linux devicetree bindings, and Open-CMSIS-Pack DFPs. That is ~4 days for most of the structured breadth, versus curating hundreds of PDFs. A new provenance tier — `svd`/`dfp`/`devicetree` at **confidence 1.0** — sits beside `kicad_bom`, because a register address in an SVD is *declared by the vendor*, not extracted with a guess. Licensing is tracked per source and made queryable, since "what can ship in an air-gapped deployment" is a real question.

### 9.3 `fs_flash` — **the in-turn rule becomes general, in SPEC 06** ✅

*(This one was unclear as written. Restating it properly.)*

SPEC 06 set a rule: agent tools never call server-mutating APIs — the agent writes local files, a human pushes. A few tools were carved out as **ACTION-class**: they *invoke* something rather than *change* something (run a verification, run a bench job, materialize firmware). Adding one requires a written amendment, so the boundary can't erode by accident.

`fs_flash` doesn't fit that category cleanly. If the agent misjudges a verification run, you waste minutes. **If it misjudges a flash, you brick a board — or a unit on a line.** Allowlisting is necessary and not sufficient.

**Decision:** destructive hardware operations require an **explicit human instruction in the current turn**. Permission cannot be inherited from a plan approved ten minutes ago. And rather than bolting that onto SPEC 08, it becomes a **general SPEC 06 primitive** — a `destructive: true` flag any tool can declare, enforced by one mechanism and one test. `fs_flash` is its first user; erase, fuse programming, and factory-line actuation will be the next.

### 9.4 Security gating — **static analysis gates the PR, as a bb workflow** ✅

Generated code is gated on static analysis before it can become a PR. Full SPEC 02 findings analysis runs on the build, not in the inner loop — the honest coupling without making every iteration expensive.

**What this changes, and it's the better half of the answer:** the gate is **a customizable bb workflow, not hardcoded policy.** Different products have different bars — a medical device and a consumer router should not share a gate. So the pipeline is declared, versioned, and reviewable like everything else:

```yaml
# .fs/workflows/authoring-gate.yaml   — VERSIONED, reviewable as a diff
version: 1
on: [pre_pr]
gates:
  - id: citations
    rule: no_quarantined_values          # §4.3 — uncited constants block
  - id: static
    run: [cppcheck, clang-tidy, misra]
    fail_on: error
  - id: secrets
    run: fs_secret_scan
    fail_on: any
  - id: build
    run: fs_build
post_merge:
  - id: findings
    run: fs_findings_analyze             # full SPEC 02 pass on the built image
```

This is also the shape customers will want to own. **A gate someone can read, edit, and argue with is worth more than a better gate they can't see** — and it's the natural place for a customer's own rules to live.

### 9.5 Instruments — **local by default, remote-capable by design** ✅

Debug-mode instruments are assumed local to the developer's machine. But the driver interface takes a **transport** (local USB, local network, or a bb host), so nothing in the design forecloses the rack. Claim/release arbitration (§4.4) works identically either way — it just needs a claim scope that can be machine-wide or fleet-wide.

**What this changes:** one extra field in `bench_device` and a transport abstraction in the driver interface. Cheap now, expensive to retrofit, and it means the same probe script runs on a desk and on the rack.

### 9.6 Production bench / SPEC 09 — **deferred** ⏸️

The manufacturing test system is a stretch right now. Deferred.

**What this changes:** phases 8i–8k build instrument drivers for the *debug* bench only. `instro` stays in the design as the production-bench adapter (§4.4.1) so the interface accommodates it later, but no ATE work is scheduled. **Revisit when Eagle's line timing firms up** — this is the piece closest to their revenue story, and it will come back.

### 9.7 Vendor documentation partnerships — **pursue** ✅

We want first-party vendor documentation deals.

**What this changes strategically:** this is a place where **Eagle is a much stronger partner than Embedder**. Embedder is a six-person startup asking silicon vendors for documentation access. Eagle is a customer buying modules at volume with existing relationships — the conversation is a commercial one, not a favor. First-party docs would put `vendor_official` at the top of the provenance ladder alongside `svd`.

**Practically:** structured data first (§4.2.1) since it needs no negotiation, partnerships in parallel, and the corpus plus the assurance layer as the durable answer if generic grounding does commoditize.
