# SPEC 01 — The Sync Engine

*Product spec. Depends on SPEC 00. This is the shared machinery every editable surface writes through: how local state is represented, how it reconciles with Assurance Studio, and what the human sees when they change something.*

---

## 1. The product idea

**Working on your product's security model should feel like working on its code.** You edit, you see a diff, you review, you commit, you push. If someone changed the same thing upstream, you find out before you overwrite them — not after.

That's the whole spec. Everything below is in service of making that true against a backend that has no optimistic concurrency, no bulk writes for most entities, and hard deletes.

---

## 2. The four classes (the classification every entity gets)

| Class | Local form | Git | Reconciliation | Examples |
|---|---|---|---|---|
| **VERSIONED** | Domain YAML in `product-security/` | ✅ tracked | Three-way vs. base snapshot | Components, zones, dataflows, assets, threats, mitigations, requirements, test plans |
| **CACHED** | SQLite rows | ✗ gitignored | Refresh only, never written | Findings bodies, SBOM packages, standards/clauses, audit log, snapshots |
| **OVERLAY** | YAML keyed by **stable business key** in `.fs/` | ✅ tracked | Three-way on the decision tuple | **VEX triage**, risk treatment/acceptance, exploitability inputs, attack-path viability, check parameters, mapping `suppressed`/`is_required` |
| **ACTION-ONLY** | Nothing stored | — | Invoked | Review transitions, verification runs, report generation, workflows |

**Classification is a design-time decision recorded in code**, not a runtime guess:

```ts
// lib/sync/registry.ts
export const ENTITIES = {
  threat:      { class: "VERSIONED", dir: "product-security/threats",     key: slugKey },
  requirement: { class: "VERSIONED", dir: "product-security/requirements", key: slugKey },
  finding:     { class: "CACHED",    table: "findings" },
  vexDecision: { class: "OVERLAY",   dir: ".fs/triage", key: findingStableKey },
  // …
} as const;
```

Adding an entity means adding a registry line plus a serializer — not a new sync implementation.

## 3. The three layers

```
Assurance Studio          system of record (others can change it)
        ▲ push                    │ pull
        │                         ▼
.fs-sync/base/            pristine accepted generation at last complete pull  (gitignored)
        ▲                         │
        │ three-way diff          ▼
product-security/ + .fs/  working model  (git-tracked, human + agent editable)
```

**Base is the load-bearing layer.** With it we compute:
- `diff(base, working)` → our changeset
- `diff(base, remote)` → upstream drift
- their intersection → **conflicts**

Without it we'd have last-write-wins, which silently destroys other people's work. Base is gitignored (it's local machinery, like `.terraform/`); a fresh clone establishes it with a pull. Base, id mappings, and every remotely pulled cache are read only through the accepted generation for the exact `project_id, project_version_id, entity_kind`; staging pages never participate in status, plan, panels, or id resolution.

**A subtlety worth designing for:** if a teammate commits a model change to git that hasn't been pushed to AS, your `status` shows it as pending. That's correct and desirable — **the model gets code review before it reaches the system of record.**

## 4. Serialization rules

**VERSIONED entities → domain-shaped YAML, not schema-shaped.** One file per entity for things that change independently; a requirement carries its verification contract inline rather than pointing at a join table.

**Three rules that matter more than they look:**

1. **Exclude server-owned fields.** Nearly every TARA entity has a block no endpoint accepts — `source`, `created_by_agent`, `review_*`, `ai_*`, `human_edited`, `processing_*`, `embedding`. **AS's own `tara_snapshot_semantic_payload()` already canonicalizes exactly this** — use it as the exclusion list rather than deriving one by hand.
2. **Reference by slug, not UUID.** `mitigates: THREAT-22` is reviewable; `mitigates: 3f8a1c2e-…` is not. `idmap.json` resolves at push time; new entities get their UUID back on create.
3. **Separate model from layout.** Canvas positions change on every drag. `product-security/layout/canvas.json`, never in the entity files.

**OVERLAY entities → keyed by stable business identity**, because the underlying record is regenerated by the platform. Every overlay file carries, per decision: the decision fields, `provenance` (who/when/evidence), and `sync.base` (the server tuple at last pull).

## 5. The commands

### `pull [surface]`
Fetch from the owning service into a new or resumed staging generation for explicit `projectId, projectVersionId`. Every page commits atomically under that staging id without changing reader-visible pointers. After all requested kinds/pages and projections validate, one SQLite transaction flips every requested accepted pointer, increments the corresponding base revisions, and only then fast-forwards clean working files. Failure or cancellation retains the old accepted generation and opaque staging continuation for retry. Refresh CACHED tables under the same rule. Emit progress via realtime.

### `status`
Three lists, always in this order: **local changes** (working vs base) · **upstream changes** (remote vs base) · **conflicts** (both). Plus orphans — overlay decisions whose stable key no longer resolves.

### `plan [surface]` — the safety mechanism
Compute the ordered changeset and **validate before showing it.** The plan is the product; the push is mechanical.

Plan output, rendered both in CLI and as a review panel:

```
Plan: 6 to create, 3 to update, 1 to delete, 2 conflicts

  + create  REQ-118  "WHEN a rollback is requested, the device SHALL…"
  ~ update  THREAT-22  severity: medium → high
  ~ update  VEX  busybox@1.36.1 / CVE-2023-42364  → NOT_AFFECTED (CODE_NOT_REACHABLE)
  - delete  DATAFLOW-9   ⚠ referenced by THREAT-14, THREAT-31

  ⚠ conflict  THREAT-07.description
       base:   "Unauthenticated access to…"
       ours:   "Unauthenticated management access to…"
       theirs: "Unauth access to mgmt iface…"  (jsmith, 2026-08-09 14:22)

  2 orphaned overlay decisions (component no longer present) — see status
```

**Validations the plan must run:**
- **Referential integrity** — deleting something that's referenced fails with the referrer list.
- **Ordering** — creates before dependents; deletes in reverse dependency order.
- **Derived-field guards** — reject writes to service-derived fields (`requirements.verification_status`, `risk_value_numeric`, `severity_level_source`, exploitability outputs). Encode the schema truth in the tool.
- **Schema/vocabulary** — methodology profile vocabularies, VEX justification/response rules, EARS well-formedness.
- **Blast radius** — a delete or a >20-entity change requires explicit confirmation.

### Review-panel apply (`push [surface]` is a handoff only)
The review panel renders the complete plan and is the intended home of a future authenticated apply. Pinned bb RPC currently provides no authenticated human actor and the plugin has no `humanApprovalCapability` mint path, so v1 apply/conflict handlers are authorization-unavailable and perform no side effects. A `confirmed` boolean, plugin token, `requestInput`, Origin/Host check, or CLI flag cannot fill that gap. The agent-readable CLI spelling `push [surface]` only validates the plan and prints/opens the review-panel route; it never mutates upstream, resolves a conflict, accepts confirmation, or exposes a bypass flag.

**Apply semantics, dictated by the backend's real shape:**
- **No bulk create/update for core entities** → per-row calls, chunked and rate-limited. **VEX is the exception** (bulk ≤500 with per-item partial success) — use it.
- **Diff before writing.** An identical re-PUT still bumps timestamps and emits an audit row. `noop` items are skipped, not re-sent.
- **Per-entity base update.** After each success, advance only that entity's exact accepted `(project, product-version/project-level, kind, key)` base/id row and increment that kind's `base_revision` in the same transaction. Apply checks the accepted generation, starting revision, and the item's expected base content hash. A failed push leaves a coherent, partially-advanced state; failed siblings stay dirty and re-plan next run.
- **Use the concurrency tokens that exist.** TARA content writes bracket between a head check and a `POST /versions` checkpoint with `expectedHeadVersionId`; review and standards lifecycle transitions use cached decimal `review_version`. Do not invent or substitute `entity_version`.
- **Read-back verification** for entities on routes where `.strict()` isn't applied — a PATCH can silently drop unknown keys, so "it returned 200" isn't proof.
- **Provenance stamping** where the API allows it (e.g. `[bb:{run-id}]` prefix in `vex_reason`), since there's no machine/human provenance column yet.

## 6. Conflict UX

Field-level, not file-level — these are records, not prose. Git's textual conflict markers are wrong here (YAML with `<<<<<<<` can be invalid).

**Presentation:** the plan lists each conflict with base / ours / theirs, plus **server audit attribution** (who and when, from the activity endpoint). Resolution is explicit per item: `take-ours`, `take-theirs`, or edit. A policy default may be set per surface — for VEX, *theirs-wins on human server edits* is sensible, because the server can't distinguish our stale write from an intentional override.

**Auto-merge** where safe: different fields on the same entity, and set-operations on graphs (node/edge adds and removes). **Never** auto-merge same-field edits.

**Residual race:** the server can change between plan and apply. Accept it — it's strictly smaller than the platform's own UI exposure, and the audit trail makes it reconstructable. If AS later exposes `vexChangedAt` and an `expected` precondition, apply upgrades to true compare-and-swap with no client redesign.

## 7. The review panel

The plan deserves a first-class UI, not just CLI output. **This is a demo moment: *the agent proposed changes to your security model — here's the exact diff — approve to push.***

- Grouped by operation (create/update/delete/conflict/orphan), collapsible.
- Each row expands to a field-level diff with the domain component rendered inline (a threat diff shows a `<ThreatCard>`, not raw YAML).
- Conflicts inline, with resolution controls.
- Footer: blast-radius summary and a single **Push** button, disabled while conflicts are unresolved.
- Post-push: per-item results with retry for failures.

**Where it lives:** a nav-panel route (`/plugins/finite-state/sync`), reachable from a status chip in every panel header showing pending-change count.

## 8. Agent affordances

| Affordance | Behavior |
|---|---|
| **Tools** | `fs_sync_status`, `fs_sync_plan` — both read-only, but note `fs_sync_plan` performs a server *read* refresh of upstream tuples for conflict detection (never a mutation); offline it degrades to the last-pulled base with a staleness warning (SPEC 06 §2.6 ⚑9). **No `fs_sync_push` tool**; v1 has no authenticated human-apply capability |
| **Skill** | `skills/sync/SKILL.md`: edit YAML with native file tools, never call mutating APIs; run `plan` to check work; hand the plan to the human review panel, which reports apply unavailable until authenticated actor proof exists |
| **Directive** | `::fs-plan{id=…}` renders the plan inline so the agent can show what it's about to propose |

## 9. Data model

The wire scope is `{projectId, projectVersionId}` with null for project-level. Storage maps null to `PROJECT_LEVEL_VERSION_ID` (`"@project"`) and rejects that literal at external boundaries. Every scoped key/FK retains both non-null SQL columns; no entity key embeds a parallel project or version scope.

```sql
CREATE TABLE base_snapshot (          -- VERSIONED + OVERLAY base, staged by generation
  project_id        TEXT NOT NULL,
  project_version_id TEXT NOT NULL,
  entity_kind       TEXT NOT NULL,
  generation_id     TEXT NOT NULL,
  entity_key        TEXT NOT NULL,
  remote_id   TEXT,                   -- owning remote-service uuid, null until created
  payload     TEXT NOT NULL,          -- canonical JSON at last pull
  content_hash TEXT NOT NULL,
  pulled_at   TEXT NOT NULL,
  PRIMARY KEY (project_id, project_version_id, entity_kind, generation_id, entity_key)
);

CREATE TABLE id_map (
  project_id        TEXT NOT NULL,
  project_version_id TEXT NOT NULL,
  entity_kind       TEXT NOT NULL,
  generation_id     TEXT NOT NULL,
  entity_key        TEXT NOT NULL,
  remote_id         TEXT NOT NULL,
  PRIMARY KEY (project_id, project_version_id, entity_kind, generation_id, entity_key),
  UNIQUE (project_id, project_version_id, entity_kind, generation_id, remote_id)
);
```

Plus `pull_generation`, `sync_state`, and `push_log` from SPEC 00. `.fs-sync/idmap.json` mirrors only the accepted mapping for one explicit project/version and labels its generation and base revision.
